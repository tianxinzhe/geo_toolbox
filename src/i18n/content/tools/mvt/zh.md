MVT（Mapbox Vector Tile）是矢量切片的事实标准。前端渲染地图时拿到的不是图片，而是一块压缩过的二进制：里面有几个图层，每个图层装着要素、属性和用整数编码的几何。这个工具把它还原成可读的图层结构和 GeoJSON，排查数据、验证导出结果，或者把切片内容接进自己的流程，都用得上。

## 输入是什么

两种入口，二选一：

- **文件**：`.pbf` 或 `.mvt`，也可以是它们经过 gzip 压缩的文件（不少服务端直接返回 gzip）。单文件上限 20 MB。
- **Base64**：把瓦片字节编码成字符串粘进来。`data:application/octet-stream;base64,` 前缀、换行、空格，以及 base64url 的 `-` `_` 都能识别。

如果拿到的是 `14_4823_6160.pbf`、`14-4823-6160.mvt` 或 `14/4823/6160.pbf` 这类文件名，z/x/y 会自动填好；其余命名请手动输入。

## 为什么还要填 z/x/y

MVT 只描述一块瓦片内部的相对位置：坐标是 0 到 `extent`（通常是 4096）之间的整数，y 轴向下。它不知道自己属于哪一层级、哪一列哪一行——这些信息由请求 URL 或容器元数据提供。

因此：

| z/x/y | 输出坐标 | 用途 |
|---|---|---|
| 已填写 | WGS84 经纬度（EPSG:4326） | 直接放进 GeoJSON 查看器、数据库或 GIS 软件 |
| 留空 | 瓦片内整数（0 到 extent） | 核对几何形状、比较不同瓦片的内部结构 |

经纬度换算按 Web Mercator 的 XYZ 方案：先由 `(x + 像素/extent) / 2^z` 求经度，再用墨卡托反算纬度。这套约定与 Google Maps、OpenStreetMap、Mapbox 的切片编号一致。

## 结果怎么读

结果区先给一行汇总：图层数、要素数、文件大小。往下是图层表：

- **图层名**：来自 Layer 的 `name`，切片服务靠它区分道路、水系、POI；
- **版本**：Layer 的 `version`，常见为 2；v1 的老瓦片一样能解析；
- **范围**：Layer 的 `extent`，几何坐标的上界，默认 4096；
- **要素**：该图层有多少条要素；
- **点 / 线 / 面**：按几何类型统计，用来快速判断图层内容符不符合预期。

## 解码细节

解析器是自己写的，不依赖第三方 protobuf 运行时，所以每个错误都能精确控制：

- **protobuf 层**：只处理 varint 与 length-delimited 两种线格式，未知字段按 wire type 跳过，保证向前兼容；
- **几何命令**：`MoveTo(1)`、`LineTo(2)`、`ClosePath(7)`，参数是 zigzag 编码的增量，逐个累加得到绝对坐标；
- **多部件**：连续的 `MoveTo` 生成多条线或多个环；点类型的 `MoveTo` 带多个计数时输出 `MultiPoint`；
- **面与洞**：按有向面积区分外环和洞。规范要求外环在屏幕坐标系里顺时针，个别编码器却反着来，工具会按多数环的方向自适应，再统一成 GeoJSON 的绕向；
- **容错**：缺少 `ClosePath` 的环自动闭合并提示；未知几何类型、损坏的几何命令、奇数个 tags 都计入警告，不会中断整块瓦片。

图层版本、extent、属性类型都按 Mapbox Vector Tile 2.x 规范处理；`srsName` 之类的坐标系声明在 MVT 中并不存在，因此这里不做任何投影变换。

## 常见用途

- **排查切片服务**：某条道路没显示，先看它在不在瓦片里、属于哪个图层、属性是否符合样式表达式；
- **验证导出**：自建切片流水线产出的 `.pbf` 合不合规范，拿解析结果和源数据对一遍；
- **提取样例**：把一块瓦片转成 GeoJSON，直接拖进 QGIS 或本站的预览工具检查；
- **教学与调试**：看清 MVT 的图层结构与几何编码，比读规范更快。

## 边界

- 只解析单张瓦片。`.mbtiles`、`.pmtiles`、`.zip` 等容器需要先取出瓦片；
- 不做坐标系变换。瓦片坐标按规范视为 Web Mercator，输出为 WGS84 经纬度；
- 不渲染地图。这个页面专注于结构解析，需要看图形请把 GeoJSON 拿到预览或绘制工具里；
- 20 MB 上限。超大瓦片通常意味着数据没按图层拆分，建议先在服务端裁剪。

## 常见问题

### 为什么必须填 z/x/y 才能拿到经纬度？

因为 MVT 的几何用整数记录瓦片内部坐标（0 到 extent），文件里并不写自己属于哪张瓦片。同一串坐标，在 14 级和 16 级指的位置完全不同，换算经纬度时非得由调用方告诉工具 z/x/y。不知道编号，坐标就原样保留，核对几何形状与属性仍然可以。

### 为什么整包 .mbtiles 或 .pmtiles 解析失败？

这两种是瓦片容器，一个包里装着很多张瓦片。解析器要的是单张 Tile 消息，容器的文件头自然被当成非法 protobuf。先用 sqlite 或 pmtiles 工具按 z/x/y 把某一张取出来，再来解析。

### 为什么有些要素被跳过了？

三类原因比较常见：要素没有声明几何类型（type 为 UNKNOWN）；几何命令被截断，或者出现了未知命令；tags 数量是奇数，导致最后一个键没有对应的值。前两类没法还原几何，第三类只丢一个属性。跳过了多少条，会写在结果区的警告里。

### 为什么同一个面在 GeoJSON 里的绕向变了？

MVT 区分外环和洞，靠的是屏幕坐标系（y 向下）里的绕向；GeoJSON 的惯例则是外环逆时针。工具先按规范把外环、内环分清楚，再统一成 GeoJSON 的绕向。结果是坐标顺序可能跟源文件相反，形状和洞的归属不会变。

### 解析会在服务器上留记录吗？

不会。文件用浏览器的 File API 读进内存，Base64 也在本页解码，没有任何网络请求，刷新页面就清空了。
