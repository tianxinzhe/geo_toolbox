CSV 和 TSV 就是最普通的表格文本。放到地理数据交付里，它们也是最容易出事的格式：没有坐标系声明，没有几何类型，全靠列名和约定撑着。

CSV 的语法还能对照 RFC 4180，TSV 只有 IANA 的 MIME 注册和长期惯例，两者都没定义「地理」这回事。一份表格能不能变成地图，取决于文件之外有没有交代清楚三件事：坐标系是哪个、哪两列是坐标、几何是点还是一列 WKT。这几件事不会让文件打不开，只会让数据错得很安静。

## 最小可用示例：两种组织方式

**经纬度两列**，适合点数据：

```csv
name,lng,lat,category
天安门,116.3974,39.9088,landmark
故宫,116.3970,39.9163,landmark
```

两列布局最省事，任何表格软件都能打开，任何语言都能读。代价是只能表达点：一个点一行，线、面都没有位置，也没有地方放几何类型。表头写 `lng,lat` 比 `x,y` 清楚得多，后者在不同软件里可能是经度，也可能是投影东坐标。文件本身不存 EPSG 代码，交付时得另写一句「WGS84 经纬度，经度在前」。

**一列 WKT 几何 + 属性列**，适合点线面混存：

```csv
name,geom,area_m2
示例范围,"POLYGON ((116.39 39.90, 116.41 39.90, 116.41 39.92, 116.39 39.90))",482000
示例道路,"LINESTRING (116.39 39.90, 116.40 39.91)",0
```

只要出现线或者面，就得用 WKT 列，否则几何会被压扁成点。WKT 值内部含逗号，整格必须用双引号包住，这是 CSV 引号规则最常被忽略的一处。读取方也需要知道哪一列是几何，常见做法是固定列名 `geom`、`geometry` 或 `wkt`。

## TSV

TSV 用制表符分隔，规则与 CSV 相同，好处是地址、名称里可以出现逗号，不用加引号：

```tsv
name	lng	lat
天安门	116.3974	39.9088
故宫	116.3970	39.9163
```

代价是制表符不能出现在字段内，复制粘贴时容易被空格替换。TSV 也没有 CSV 那样通行的引号转义规则：字段里真的出现制表符或换行，多数解析器没有标准做法。所以 TSV 更适合由程序生成、由程序读取，不太适合人工在聊天窗口里传抄。

## 结构与字段说明

| 项目 | 规则 | 是否必需 | 常见取值 |
|---|---|---|---|
| 记录分隔 | 一条记录一行，RFC 4180 用 CRLF | 必需 | CRLF、LF |
| 字段分隔 | CSV 用逗号，TSV 用制表符 | 必需 | `,`、`\t`、`;`（欧洲变体） |
| 表头 | 名称与列数应与数据行一致 | 规范中可选，实际必需 | `lng,lat,name` |
| 坐标列 | 经度列与纬度列各一，或一列 WKT | 必需 | `lng`/`lon`/`x`、`lat`/`y` |
| 引号 | 含分隔符、引号或换行的字段 | 按需 | `"a,b"`、`"say ""hi"""` |
| 编码 | 规范不规定；实践以 UTF-8 为主 | 必需，但常被忽略 | UTF-8、UTF-8 BOM、GBK |
| 坐标系 | 格式中无此字段 | 无法写入文件 | 需在说明中写 EPSG:4326 |

有几条细节容易混淆，单独记一下。RFC 4180 允许最后一条记录带或不带结尾换行，文件末尾多一个换行不算错；连续两个换行就是一条空记录，跳不跳过由读取方决定。字段首尾的空格属于字段内容，规范没要求解析器删除，` 116.3974` 这样的值得自己 trim。引号内的换行合法，一条记录可以占多行，所以不能按行数判断记录数。数字在 CSV 里没有类型：`116.3974` 和 `"116.3974"` 都是文本，当不当数值解释由读取方定。

编码不在 RFC 4180 的范围内。MIME 注册的 `text/csv` 允许带 `charset` 参数，文件自己不说时，读取方只能猜。UTF-8 和 GBK 对同一串字节的解释不同，中文列名和中文属性会最先暴露问题。

## 常见错误与陷阱

### 编码与 BOM

**现象**：表头看着是 `lng`，前面却多了一个不可见字符；或者整列中文成了乱码、问号。

**原因**：文件用 GBK 保存，或者 UTF-8 带了 BOM。按 UTF-8 读时，BOM 会并进第一个字段；Windows 上的 Excel 打开无 BOM 的 UTF-8 CSV，则会退回本地代码页。

**后果**：列名匹配失败，工具报找不到经纬度列；就算按位置强行映射，首列坐标也解析不出来。BOM 这类错误一般只影响第一列，很容易被当成「数据本身有问题」。

### 逗号与引号

**现象**：某一行拆出的列比表头多，后面的属性整体右移。

**原因**：字段里有逗号（地址、WKT、名称）却没加引号，或者字段里的双引号只写了一个。RFC 4180 要求引号内的引号写成两个。

**后果**：列错位。经纬度可能落进属性列，轻则整行被跳过，重则纬度当经度读入，得到一批看着合法、位置却错了的点。

### 分号与小数字符

**现象**：整份文件只解析出一列，或者坐标偏移上千公里。

**原因**：欧洲区域设置常用分号分隔、逗号当小数点，导出的文件是 `name;lng;lat`、`116,3974`。

**后果**：按逗号切分，`116,3974` 成了 `116` 和 `3974` 两个值，坐标直接错位；按分号切分，又得读取方事先知道这一点。文件里没有声明分隔符的字段，只能靠约定或人工确认。

### 经纬度顺序

**现象**：点全落在南极附近、西半球，或者整体沿对角线镜像。

**原因**：表头只写 `x,y`，或者写成 `lat,lng`，读取方按通行的「经度在前」处理。

**后果**：经纬度互换。纬度绝对值超过 90 会被范围校验拦住，小于 90 就当成合法点，混在几万条记录里肉眼几乎看不出来。

### 空行、多行表头与尾随空白

**现象**：第一条数据被当成表头，或者记录数比预期少。

**原因**：文件开头有标题行、说明行、导出时间；中间夹着空行；末尾多出几列空白。

**后果**：列映射整体错位，或者坏行被静默跳过。空行跳过后文件照样能读，问题往往到出图时才发现少了一条。

### 坐标系缺省

**现象**：坐标数值看着正常，叠到地图上却整体偏几百米甚至几公里。

**原因**：源数据是投影坐标（比如 UTM 米制），或者用了另一个基准面，CSV 里没有任何地方记坐标系。

**后果**：文件没法自解释，错误也没法从文件本身恢复。米制坐标通常在范围校验时暴露；几百米的基准面差异则完全看不出来，只能回源头确认。

## 与相邻格式对比

| 格式 | 几何能力 | 属性 | 坐标系 | 典型用途 |
|---|---|---|---|---|
| CSV / TSV | 点；线面需 WKT 列 | 任意列 | 无声明 | 交换、批量录入、导入数据库 |
| Excel（XLSX） | 点；线面需 WKT 列 | 任意列，带格式 | 无声明 | 人工整理、核对 |
| WKT 文本 | 点线面，一行一个 | 无 | 可带 SRID 前缀 | 粘贴单个几何 |
| GeoJSON | 点线面全集 | 有 | 默认 WGS84 | 网页地图、接口 |

表格格式的强项是通用：数据库、电子表格、脚本语言都能直接读。弱项是它只描述值，不描述含义。需要几何类型、坐标系和嵌套属性，GeoJSON 更合适；只描述一个几何，WKT 更直接；交付前要反复人工核对，Excel 顺手，但它不适合做程序之间的交换格式。

## 转换与工具入口

要把表格转成矢量数据，用[矢量格式转换](/zh/tools/format-convert/)：全是点就写 `lng,lat`，含线面就写 WKT 列。源数据是投影坐标的话，先用[投影坐标转换](/zh/tools/epsg-convert/)换到 EPSG:4326，再回来转格式。表格与电子表格的差别见 [Excel 坐标数据详解](/zh/guide/excel/)，其他格式怎么取舍见 [15 种矢量格式总览](/zh/guide/vector-formats/)。

## 示例数据与解析脚本

- [sample.csv](/examples/data/sample.csv)、[csv_parser.py](/examples/python/csv_parser.py)
- [sample.tsv](/examples/data/sample.tsv)、[tsv_parser.py](/examples/python/tsv_parser.py)

两份样例描述同一组内容：时代广场的点与一条步行线。脚本只用 Python 标准库，按表头识别经纬度列，输出 GeoJSON `FeatureCollection`：

```bash
python csv_parser.py sample.csv -o out.geojson
python tsv_parser.py sample.tsv
```

列名匹配会忽略大小写、空格、下划线和连字符；识别不到就报错，不会擅自把第一列当经度。坐标缺失或解析不了的行会被跳过。
