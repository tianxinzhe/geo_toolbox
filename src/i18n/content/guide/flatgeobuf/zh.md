FlatGeobuf（`.fgb`）是为「快速读取、流式处理、按空间范围过滤」设计的二进制矢量格式。它基于 FlatBuffers，常被用作 Web 地图和大型数据集的传输格式。

它不是一个 OGC 标准，而是由开源社区维护的规范，配套实现覆盖多种语言。设计目标很明确：一个文件、不需要附带文件、打开就能按空间范围取数据。相比通用数据库容器，它牺牲了多图层和就地编辑，换来了顺序读取和网络传输上的效率。

## 最小可用示例

1. **文件头**：magic 标识、版本、要素数量、图层 schema（字段名与类型）。
2. **空间索引**：默认打包 R-tree，记录每个要素的包围盒。
3. **要素数据**：逐条存储几何与属性，可以顺序读取。

因为索引在前，客户端可以先读索引，判断哪些要素落在当前视野，再只下载命中的部分。这对 Web 地图很有价值：不必先下载整个文件。

按字节顺序看，文件大致是这样排列的：

```text
magic "fgb\x03fgb\x00"   8 字节
header 长度              4 字节，小端
header                   FlatBuffers：schema、要素数、几何类型、可选 CRS
[空间索引]               打包 Hilbert R-tree，可选
要素记录                 4 字节长度 + FlatBuffers 要素，重复到文件结束
```

一个最小可用的文件只需要 magic、header 和要素记录。空间索引是可选的：写入端生成索引后，读取端才能按范围跳转；如果没有索引，就只能从头顺序扫描。

## 结构与字段说明

| 部分 | 内容 | 是否必需 | 说明 |
|---|---|---|---|
| magic | 8 字节文件标识 | 必需 | 用来区分其他二进制格式 |
| header | schema、要素数、几何类型、可选 CRS | 必需 | FlatBuffers 编码，长度固定写在前面 |
| 空间索引 | 打包 Hilbert R-tree | 可选 | 记录要素包围盒与偏移 |
| 要素记录 | 4 字节长度 + 要素内容 | 必需 | 顺序存放，可流式读取 |
| 要素内容 | 几何、属性、可选 id | 必需 | 几何用 FlatBuffers 结构表达 |

header 里的 schema 定义字段名和类型，类型比 Shapefile 丰富，包括不同位宽的整数、浮点、布尔、字符串和 JSON 等。字段名没有 10 字符限制，中文名也可以正常保存。

坐标系信息是可选的。规范允许在 header 里写 CRS 描述，但很多写出端不填，读取端只能按数据本身的数值范围判断。若要把文件直接叠到 Web 底图，最好在导出时明确坐标系并转换到 WGS84。

几何用 FlatBuffers 的联合类型表达，点、线、面、多部件和几何集合各有自己的结构，坐标以双精度数组存储。它不用 WKB，所以不能把 WKB 字节直接塞进来，转换时要经过几何库。

## 特点

- **没有 10 字符字段名限制**，字段类型更完整。
- **单文件、单图层**，多图层需要多个文件。
- **支持流式处理**，适合大数据和按需加载。
- **文件比 GeoJSON 小**，解析也更快。
- **有空间索引**，范围查询不需要全表扫描。

索引在文件前部，这一点是流式读取的关键。客户端读 header 和索引后，可以计算出命中要素的字节区间，用 HTTP Range 请求只取这些片段；服务端只要支持 Range，就能把一个大文件当成可查询的数据源，而不必部署数据库。

## 限制

- **不可读**：不能用文本编辑器打开，出问题必须用专门工具。
- **单图层**：不能像 GeoPackage 一样在一个文件里放多个图层。
- **写入后修改不灵活**：通常整文件重写，不适合频繁编辑。
- **生态比 Shapefile / GeoPackage 小**，老旧软件可能不支持。

索引虽然默认生成，但规范允许省略。这导致同一个后缀的文件行为不同：有索引时按范围读取很快，没有索引时读取库可能报错，或者退化成全量扫描。拿到 `.fgb` 后先确认它是否带索引，比直接假设更稳妥。

## 常见错误与陷阱

**用文本编辑器打开，看到乱码**：现象是满屏不可读字符，被误判为文件损坏；原因是内容本身就是二进制；后果是浪费时间排查，正确的做法是用 GDAL 或专用库读取。

**假设文件一定带空间索引**：现象是某个读取库报错，提示节点大小不合法；原因是一些导出器只写 header 和要素，索引节点数为空；后果是按范围读取失败，需要改成顺序解析或重新生成索引。

**HTTP 服务不支持 Range 请求**：现象是前端按范围加载时仍然下载整文件；原因是服务器返回完整响应，忽略 Range 头；后果是按需加载失效，带宽和首屏时间都受影响。

**把多图层数据导出成一个 `.fgb`**：现象是只保留了第一个图层；原因是格式本身只支持单图层；后果是其余图层静默丢失，导出前必须拆分。

**没有声明坐标系却直接叠加**：现象是数据出现在错误位置或比例异常；原因是 header 里的 CRS 为空，读取端按默认经纬度处理；后果是叠加错位，需要在源头转换坐标。

## 与相邻格式对比

| 维度 | FlatGeobuf | GeoPackage | Shapefile | GeoJSON |
|---|---|---|---|---|
| 文件数量 | 单个文件 | 单个数据库文件 | 多个同名文件 | 单个文本文件 |
| 图层 | 单图层 | 多图层、含瓦片 | 单图层 | 单集合 |
| 空间索引 | 打包 Hilbert R-tree | R-tree 表 | 依赖附带索引 | 无 |
| 流式与 Range | 支持 | 不支持 | 不支持 | 不支持 |
| 体积 | 较小 | 中等偏大 | 中等 | 最大 |
| 可读性 | 二进制，不可读 | 二进制，需 SQLite | 二进制加文本 | 纯文本 |
| 编辑 | 整文件重写 | 就地更新 | 有限 | 直接编辑 |

### 适用场景

| 场景 | 是否适合 |
|---|---|
| Web 地图按视野加载 | 适合 |
| 几十万到上百万要素的只读数据 | 适合 |
| 需要多图层管理 | 不适合，用 GeoPackage |
| 需要人工检查文件内容 | 不适合，用 GeoJSON |
| 传统 GIS 交付 | 先确认对方支持 |

## 转换与工具入口

FlatGeobuf 转 GeoJSON 会展开为普通要素集合，属性保留；反过来，多图层或复杂样式无法写入。

导出时最好一次只处理一个图层，并在导出后确认文件大小与要素数量是否合理。如果下游要按范围加载，还要检查索引是否生成、服务器是否支持 Range 请求。需要互转时用 [矢量格式转换](/zh/tools/format-convert/)；与 GeoPackage 的对比见 [GeoPackage](/zh/guide/geopackage/)，字段与几何结构的参考见 [GeoJSON](/zh/guide/geojson/)。

## 示例数据与解析脚本

[sample.fgb](/examples/data/sample.fgb) 是一个只有几百字节的最小示例，包含文件头、空间索引和少量要素，可以用来验证读取顺序。

[flatgeobuf_parser.py](/examples/python/flatgeobuf_parser.py) 直接按字节解析：校验 magic、读 header 长度、根据索引节点大小决定是否跳过索引，再逐条解码要素并输出 GeoJSON。它不依赖读取库的索引校验，因此对没有索引的文件也能工作。

```text
python flatgeobuf_parser.py sample.fgb -o out.geojson
```

如果脚本提示 bad magic，先确认文件没有在传输中被当作文本处理；如果要素数为 0，检查 header 是否完整。
