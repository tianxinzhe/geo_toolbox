GPS 设备、运动手表、轨迹应用基本都认 GPX。它本质是一份 XML，用来记录航点、轨迹和路线，结构不复杂，绝大多数户外软件都能直接导入。

## 最小可用示例

核心元素就三样：

- `<wpt>`：航点，一个独立的坐标点。
- `<trk>`：轨迹，下面挂若干 `<trkseg>` 段，每段再由若干 `<trkpt>` 组成。
- `<rte>`：路线，由 `<rtept>` 串起来，多数时候表示规划出的路径，不是实际走出来的记录。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<gpx version="1.1" creator="GeoToolbox"
     xmlns="http://www.topografix.com/GPX/1/1">
  <wpt lat="39.9088" lon="116.3974">
    <name>天安门</name>
    <ele>44.0</ele>
  </wpt>
  <trk>
    <name>晨跑</name>
    <trkseg>
      <trkpt lat="39.9088" lon="116.3974"><time>2026-11-09T06:00:00Z</time></trkpt>
      <trkpt lat="39.9095" lon="116.3981"><time>2026-11-09T06:00:30Z</time></trkpt>
    </trkseg>
  </trk>
</gpx>
```

三类元素可以共存于同一个文件。要同时写，按 `wpt`、`rte`、`trk` 的顺序放最保险。多数软件不怎么管顺序，但真拿 schema 去校验时会较真。

## 结构与字段说明

元素集合是定死的，想加自己的东西只能走 `extensions`。常用部件见下表。

| 元素或属性 | 是否必需 | 常见取值或单位 |
| --- | --- | --- |
| `<gpx>` | 必需，作为根元素 | 需带 `version` 与 `creator` 属性 |
| `<metadata>` | 可选 | 文件级名称、描述、作者、时间和范围 |
| `<wpt lat lon>` | 航点必需 | 十进制度，WGS84 |
| `<trk>`、`<trkseg>`、`<trkpt lat lon>` | 轨迹必需 | 一条轨迹可有多段，每段至少两个点 |
| `<rte>`、`<rtept lat lon>` | 路线必需 | 通常表示规划路径 |
| `<ele>` | 可选 | 海拔，单位米 |
| `<time>` | 可选 | ISO 8601 UTC 时间，带 `Z` 后缀 |
| `<name>`、`<desc>`、`<sym>`、`<type>` | 可选 | 名称、描述、符号与分类 |
| `<extensions>` | 可选 | 自定义命名空间，需放在元素末尾 |
| `<link>` | 可选 | 关联网页，替代旧版的 url 字段 |

`lat` 和 `lon` 是属性，不是子元素，并且纬度必须写在前面、经度在后。单位一律十进制度，不能写度分秒。海拔按米算；时间要是带时区的 ISO 8601 字符串。少写时区的话，程序会默认按 UTC 理解，整体就差出几个小时。

## 坐标与字段

- **经纬度放在 `lat` / `lon` 属性里**，顺序和 KML 的 `<coordinates>` 正好反过来。
- **坐标系固定 WGS84**。
- **常用子元素**：`<ele>` 海拔、`<time>` 时间、`<name>` 名称、`<desc>` 描述、`<sym>` 符号。
- **时间统一用 UTC**，末尾带 `Z`，本地时区得自己换算。

海拔和时间能逐点携带，这是 GPX 跟普通线格式拉开差距的地方。同一组子元素，航点、轨迹点、路线点都能用。不过软件不一定都读：`sym` 和 `type` 这类字段，往往只在某些设备或平台上才有意义。

## 轨迹抽稀与时间戳

原始轨迹通常按固定间隔采点，点密、精度高，直接展示或者入库，体积会很吃紧。常见的处理是按距离或按形状抽稀，比如用 Douglas-Peucker 这类算法，在给定容差内只保留转折点。抽稀动了形状，也把删掉那些点上的时间和海拔一起扔了，所以得先想清楚用途：导航要留住转弯细节，统计里程更看重整体轮廓。

速度、停留、分段这些计算都靠时间戳。设备暂停、丢信号或者手动分段的时候，应该新开一个 `<trkseg>`，别把断开的两点直接连上——那样会画出一条横穿地图的直线，速度也跟着离谱。抽稀后如果还保留原始时间序列，要核对点数对得上时间数，并且时间保持单调递增。

不管抽不抽稀，原始文件都留一份，需要的时候还能重新处理。

## 常见错误与陷阱

- **把 KML 的经纬度顺序照搬过来**：轨迹会落到错误的位置。原因无非是在 `lat` / `lon` 里写反了，或者把坐标写成了子元素。解析可能直接失败，也可能位置全错却不给任何提示。
- **时间不带时区**：导入后整体偏移几个小时。写的是本地时间，程序却按 UTC 解释，于是对齐其他轨迹、算速度、看日出日落，全都不准了。
- **间断点被连成一段**：轨迹里冒出长直线和异常高速。暂停或丢星之后没开新的 `trkseg`，里程和配速统计就没法用了。
- **扩展字段放错位置**：严格校验时报 schema 错误。自定义元素没放进 `<extensions>`，或者没放在末尾，结果是部分软件直接拒收，扩展数据也读不到。
- **抽稀过头**：环形路线被拉直，转弯没了。容差设得太大，轨迹形状失真，基于轨迹做的面积和覆盖分析也就不靠谱了。
- **拿 GPX 存面**：导入后只剩一条闭合线。GPX 设计上就没有面类型，面积、内部空洞、拓扑关系全丢，还原不了。

## 限制

- **没有面**：地块、边界、行政区都表达不了，硬写进去也只是闭合线。
- **属性固定**：除了名称、描述、时间、海拔，没有通用的位置放业务字段。
- **扩展命名空间兼容性差**：厂商自定义的字段，换了软件常被忽略。
- **不适合大数据**：逐点 XML 体积大，十万个点就很臃肿了。

GPX 本身也不声明坐标系，WGS84 只是个隐含约定。要投影坐标、复杂属性或者面状数据，换 GeoJSON、GeoPackage、Shapefile 更合适。GPX 的位置，更像是设备采集和轨迹交换之间的一个中间格式。

## 与相邻格式对比

| 维度 | GPX | KML | GeoJSON |
| --- | --- | --- | --- |
| 几何类型 | 点、线（轨迹与路线） | 点、线、面及集合 | 点、线、面及集合 |
| 坐标写法 | `lat` / `lon` 属性 | `经度,纬度` 文本 | 经度、纬度数组 |
| 时间与海拔 | 一等字段，逐点可带 | 时间轴元素，海拔在坐标中 | 放入 properties |
| 样式 | 无 | 强 | 无 |
| 体积 | 中，逐点标签多 | 中 | 小 |
| 典型场景 | GPS 记录、运动与户外 | 地球浏览与展示 | Web 接口与前端渲染 |

GPX 和 KML 都常用在户外，但各管一段：GPX 记“走过的点”，时间、海拔、分段是重点；KML 管“要展示什么”，样式、气泡、图标说了算。GeoJSON 更通用，能表达面，属性结构也自由，只是不带 GPS 设备那套约定，时间和海拔得自己定字段。

## 转换与工具入口

GPX 转成 GeoJSON，轨迹变 LineString，航点变 Point，时间和海拔一般进属性。反方向就不行，面数据塞不进 GPX，只能取边界或者降级成线。互转用 [矢量格式转换](/zh/tools/format-convert/)；偏展示的格式看 [KML](/zh/guide/kml/)，通用 JSON 结构看 [GeoJSON](/zh/guide/geojson/)。

多段轨迹转换前得定一件事：输出一个 MultiLineString，还是拆成多条独立的线。前者保留“同一次记录”的意思，后者方便按段过滤。时间字段最好统一成带时区的字符串，免得不同工具各按本地时间解释。

## 示例数据与解析脚本

仓库里有示例轨迹 [sample.gpx](/examples/data/sample.gpx)，配套解析脚本 [gpx_parser.py](/examples/python/gpx_parser.py)。脚本只用 Python 标准库：`wpt` 转 Point，`trk` 的各段转 LineString 或 MultiLineString，`rte` 转 LineString；`name`、`desc`、`type`、`time`、`ele` 放进属性，海拔不写进坐标，所以输出还是二维的。GPX 没有面类型，脚本也不做重投影。用法：`python gpx_parser.py sample.gpx -o out.geojson`。
