GPX 是 GPS 设备、运动手表和轨迹应用的事实标准。它用 XML 记录航点、轨迹和路线，结构简单，几乎所有户外软件都能导入。

## 最小可用示例

- `<wpt>`：航点，一个独立坐标。
- `<trk>`：轨迹，由若干 `<trkseg>` 段组成，每段包含若干 `<trkpt>`。
- `<rte>`：路线，由若干 `<rtept>` 组成，通常表示规划路径而非实际记录。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<gpx version="1.1" creator="GeoToolbox"
     xmlns="http://www.topografix.com/GPX/1/1">
  <wpt lat="39.9088" lon="116.3974">
    <name>天安门</name>
    <ele>44.0</ele>
  </wpt>
  <trk>
    <name>晨跑</name>
    <trkseg>
      <trkpt lat="39.9088" lon="116.3974"><time>2026-11-09T06:00:00Z</time></trkpt>
      <trkpt lat="39.9095" lon="116.3981"><time>2026-11-09T06:00:30Z</time></trkpt>
    </trkseg>
  </trk>
</gpx>
```

三类元素可以同时出现在一个文件里，顺序按 `wpt`、`rte`、`trk` 排列最稳妥。多数软件对顺序宽容，但按 schema 校验时会严格要求。

## 结构与字段说明

GPX 的元素集合是固定的，扩展只能通过 `extensions` 进行。下表列出常用部件。

| 元素或属性 | 是否必需 | 常见取值或单位 |
| --- | --- | --- |
| `<gpx>` | 必需，作为根元素 | 需带 `version` 与 `creator` 属性 |
| `<metadata>` | 可选 | 文件级名称、描述、作者、时间和范围 |
| `<wpt lat lon>` | 航点必需 | 十进制度，WGS84 |
| `<trk>`、`<trkseg>`、`<trkpt lat lon>` | 轨迹必需 | 一条轨迹可有多段，每段至少两个点 |
| `<rte>`、`<rtept lat lon>` | 路线必需 | 通常表示规划路径 |
| `<ele>` | 可选 | 海拔，单位米 |
| `<time>` | 可选 | ISO 8601 UTC 时间，带 `Z` 后缀 |
| `<name>`、`<desc>`、`<sym>`、`<type>` | 可选 | 名称、描述、符号与分类 |
| `<extensions>` | 可选 | 自定义命名空间，需放在元素末尾 |
| `<link>` | 可选 | 关联网页，替代旧版的 url 字段 |

`lat` 与 `lon` 是属性而不是子元素，且顺序固定为纬度在前、经度在后。单位统一为十进制度，不使用度分秒。海拔以米计，时间必须是带时区的 ISO 8601 字符串；缺少时区的时间会被按 UTC 解释，从而产生几个小时的整体偏移。

## 坐标与字段

- **经纬度写在 `lat` / `lon` 属性里**，顺序与 KML 的 `<coordinates>` 相反。
- **固定 WGS84**。
- **常用子元素**：`<ele>` 海拔、`<time>` 时间、`<name>` 名称、`<desc>` 描述、`<sym>` 符号。
- **时间用 UTC**，带 `Z` 后缀，本地时区要自行换算。

海拔和时间都可以逐点出现，这正是 GPX 与普通线格式的区别。航点、轨迹点和路线点各自支持同一组子元素，但并不是每个字段都会被所有软件读取；`sym` 和 `type` 往往只在特定设备或平台上有意义。

## 轨迹抽稀与时间戳

原始轨迹常按固定间隔记录，点数多、精度高，但直接展示或入库会带来体积压力。常见做法是按距离或形状抽稀，例如用 Douglas-Peucker 一类算法在给定容差内保留转折点。抽稀会改变轨迹形状，也会丢掉被删点上的时间和海拔，因此需要先明确用途：导航要保留转弯细节，统计里程则更在意整体形状。

时间戳决定速度、停留和分段的计算。设备暂停、信号丢失或手动分段时，应开启新的 `<trkseg>`，而不是把间断点直接相连，否则会出现一条横穿地图的直线和异常速度。抽稀后如果保留原始时间序列，要确认点数与时间数量一致，并保持时间单调递增。

抽稀前后都应保留原始文件，以便需要时重新处理。

## 常见错误与陷阱

- **经纬度顺序照搬 KML**：现象是轨迹落到错误位置；原因是在 `lat` / `lon` 属性里写反，或把坐标写成子元素；后果是解析失败或位置全错，且没有明显报错。
- **时间不带时区**：现象是导入后整体偏移数小时；原因是写了本地时间却按 UTC 解释；后果是与其他轨迹对齐、速度计算和日出日落分析全部失真。
- **把间断点连成一段**：现象是轨迹中出现长直线和异常高速；原因是暂停或丢星后没有新开 `trkseg`；后果是里程和配速统计不可用。
- **扩展字段位置错误**：现象是严格校验时报 schema 错误；原因是把自定义元素放在 `<extensions>` 之外或不在末尾；后果是文件被部分软件拒收，扩展数据也读不到。
- **抽稀过度**：现象是环形路线被拉直、转弯消失；原因是容差设得过大；后果是轨迹形状失真，基于轨迹的面积和覆盖分析不再可靠。
- **用 GPX 存面数据**：现象是导入后只剩一条闭合线；原因是 GPX 设计上没有面类型；后果是面积、内部空洞和拓扑关系全部丢失，无法还原。

## 限制

- **没有面**：地块、边界、行政区无法表达，强行写入只能得到闭合线。
- **属性固定**：除名称、描述、时间、海拔外，没有通用的业务字段位置。
- **扩展命名空间兼容性差**：厂商自定义字段在其他软件里常被忽略。
- **不适合大数据**：逐点 XML 体积大，十万个点会非常臃肿。

GPX 也不声明坐标系，WGS84 是隐含约定。需要投影坐标、复杂属性或面状数据时，应换用 GeoJSON、GeoPackage 或 Shapefile；GPX 更适合作为设备采集与轨迹交换的中间格式。

## 与相邻格式对比

| 维度 | GPX | KML | GeoJSON |
| --- | --- | --- | --- |
| 几何类型 | 点、线（轨迹与路线） | 点、线、面及集合 | 点、线、面及集合 |
| 坐标写法 | `lat` / `lon` 属性 | `经度,纬度` 文本 | 经度、纬度数组 |
| 时间与海拔 | 一等字段，逐点可带 | 时间轴元素，海拔在坐标中 | 放入 properties |
| 样式 | 无 | 强 | 无 |
| 体积 | 中，逐点标签多 | 中 | 小 |
| 典型场景 | GPS 记录、运动与户外 | 地球浏览与展示 | Web 接口与前端渲染 |

GPX 与 KML 都常用于户外场景，但分工不同：GPX 记录"走过的点"，时间、海拔和分段是核心；KML 描述"要展示什么"，样式、气泡和图标是核心。GeoJSON 更通用，能表达面且属性结构自由，但不带 GPS 设备那套约定，需要自行定义时间和海拔字段。

## 转换与工具入口

GPX 转 GeoJSON 后，轨迹会变成 LineString，航点变成 Point，时间和海拔通常进入属性；反过来，面数据无法写入 GPX，只能取边界或降级为线。需要互转时用 [矢量格式转换](/zh/tools/format-convert/)，展示导向的格式见 [KML](/zh/guide/kml/)，通用 JSON 结构见 [GeoJSON](/zh/guide/geojson/)。

多段轨迹转换时要决定输出一个 MultiLineString 还是多条独立线；前者保留"同一次记录"的语义，后者便于按段过滤。时间字段建议统一为带时区的字符串，避免不同工具各按本地时间解释。

## 示例数据与解析脚本

仓库提供示例轨迹 [sample.gpx](/examples/data/sample.gpx) 和解析脚本 [gpx_parser.py](/examples/python/gpx_parser.py)。脚本只用 Python 标准库：`wpt` 转为 Point，`trk` 的各段转为 LineString 或 MultiLineString，`rte` 转为 LineString；`name`、`desc`、`type`、`time` 和 `ele` 进入属性，海拔不写入坐标，因此输出仍是二维。GPX 没有面类型，脚本也不做重投影。用法为 `python gpx_parser.py sample.gpx -o out.geojson`。
