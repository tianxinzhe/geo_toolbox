WKT（Well-Known Text）是 OGC 定义的几何文本表示法。它只管几何，不携带属性，放在数据库字段、日志里，或者做单条几何交换都很合适。

## 最小可用示例

```text
POINT (116.3974 39.9088)
LINESTRING (116.39 39.90, 116.40 39.91, 116.41 39.92)
POLYGON ((116.39 39.90, 116.41 39.90, 116.41 39.92, 116.39 39.90))
MULTIPOLYGON (((116.39 39.90, 116.41 39.90, 116.41 39.92, 116.39 39.90)))
GEOMETRYCOLLECTION (POINT (116.3974 39.9088), LINESTRING (116.39 39.90, 116.40 39.91))
```

- **坐标顺序是 x y**，地理场景通常就是经度、纬度。
- **多边形双层括号**：外层是环列表，内层是一个环；第一个是外环，其余是洞。
- **环必须闭合**，首尾坐标相同。
- **支持 Z / M**：`POINT Z (116.3974 39.9088 44)`。

除了上面五种，`MULTIPOINT`、`MULTILINESTRING` 以及 `POINT EMPTY`、`GEOMETRYCOLLECTION EMPTY` 这类空几何也常用。空几何的意思是位置未知但记录还在；数据库导出时它可能被写成 `NULL`，也可能直接省掉，读取时得把这两种情况分开处理。

## 结构与字段说明

WKT 里只有类型关键字和坐标，没有键值对，也没有属性表。解析器一般读到括号才开始收集数字，所以空格、逗号、括号的数量必须严丝合缝。

| 组成 | 是否必需 | 常见取值或单位 |
| --- | --- | --- |
| 类型关键字 | 必需 | POINT、LINESTRING、POLYGON、MULTIPOINT、MULTILINESTRING、MULTIPOLYGON、GEOMETRYCOLLECTION |
| 维度标记 | 可选 | Z 表示高程，M 表示度量，ZM 表示两者；省略即二维 |
| 坐标元组 | 点、线、面均需要 | 数字之间用空格分隔；地理坐标通常是十进制度 |
| 括号层级 | 必需 | 点一层，线一层，面两层，多重面三层 |
| 环闭合 | 多边形必需 | 首尾坐标完全相同，合法环至少四个点 |
| SRID 前缀 | 标准中不存在 | 仅 PostGIS EWKT 使用，写法为 `SRID=4326;` |

坐标本身不标单位。`116.3974` 可能是度，也可能是米，只能靠外部约定去判断。地理坐标系一般当经纬度读，投影坐标系按米或英尺算；两者混着用通常不报错，只是位置全错。Z 值的单位也一样，常见是米，文件里并不会写明。

同一个几何，在不同规范版本里的写法并不完全一致。较新的文本规范允许把维度标记写在类型名后面，也允许集合里再嵌集合；旧解析器也许只认二维写法。跨系统传数据之前，拿一小段样本让目标工具先解析一次，比通读整份规范快得多。

## SRID 与 EWKT

标准 WKT 不含坐标系。数据库里常能看到这种写法：

```text
SRID=4326;POINT (116.3974 39.9088)
```

这是 PostGIS 的 EWKT 扩展。见到 SRID 前缀，先确认目标工具认不认；不支持的解析器会把整串直接判为非法。

EWKT 只活在 PostGIS 生态里。带前缀的字符串用 `ST_GeomFromEWKT` 读，用 `ST_AsEWKT` 输出；换成 `ST_GeomFromText`，SRID 就得作为第二个参数传进去，字符串里不能再带前缀。数据库列一般自带 SRID 约束，导出成纯 WKT 后这层信息就没了，跨系统传递得另外记下来。

## 常见错误与陷阱

- **经纬度写反**：点落到了地球另一侧，甚至海里；毛病出在把纬度写在前头；地图照样加载，位置却全错，还不报任何错。
- **环没有闭合**：导入时提示 ring not closed，或者面积算出来是零；首尾坐标只写了一遍；这条记录会被拒收，批量导入时甚至整批中断。
- **括号层级不对**：解析器直接报语法错误；POLYGON 写成了单层括号，或者 MULTIPOLYGON 少了一层；整个文件读不进去，错误还往往出现在很靠后的位置。
- **把 EWKT 当成通用 WKT**：转换工具报非法几何；字符串前面多带了 `SRID=4326;`；要么整串被拒，要么前缀被悄悄剥掉，坐标按错误的坐标系解释。
- **随意截断小数位**：相邻点重合到一起，线条出现锯齿；只保留了两位或三位小数；测量精度永久损失，也没法从输出反推原始坐标。
- **多边形自相交**：面积算出异常值，空间查询还漏结果；环的边彼此交叉；有些数据库允许写入、却把几何标成无效，后续叠加分析就不可信。

## 限制

- **只能表达一条几何**：多个要素需要多行或多条记录。
- **没有属性**：业务字段必须另存。
- **没有样式与时间**。
- **坐标精度完全依赖写出的字符串**，不要用固定小数位截断测量数据。

WKT 同样不表达拓扑关系。相邻多边形各存各的公共边，改一处边界就得同步两处；要共享边，得换成拓扑格式。文本还有个代价：同样的坐标以字符存、不以二进制存，还常常重复，百万级要素时体积和解析时间都吃亏。

可读性也带来一个好处：几何变化能直接出现在 diff 里，版本管理省事。代价是没法像二进制那样按字节校验，手改一个数字几何就变了，还留不下修改痕迹。

## 与相邻格式对比

| 维度 | WKT | GeoJSON | WKB |
| --- | --- | --- | --- |
| 数据范围 | 单条几何，可嵌套集合 | 要素集合，含属性 | 单条几何，二进制 |
| 坐标系 | 本身不声明，EWKT 例外 | 固定 WGS84 | 由外部约定 |
| 可读性 | 高，纯文本 | 高，JSON | 低，需要解码 |
| 体积 | 小 | 较大，键名重复 | 最小 |
| 属性能力 | 无 | 有 properties | 无 |
| 典型用途 | 数据库字段、日志、测试用例 | Web 传输、前端渲染 | 数据库内部存储、批量传输 |

WKT 和 WKB 描述的是同一套几何模型，区别只在编码。WKB 用字节表示类型和坐标，体积更小、解析更快，但人读不了，适合程序之间传。GeoJSON 多了属性和集合结构，适合浏览器和 HTTP 接口，代价是键名重复，体积膨胀。属性和文本可读性都要，选 GeoJSON；只需要一条几何、想直接贴进 SQL 或日志，WKT 更省事。

## 转换与工具入口

WKT 转 GeoJSON 时，SRID 要么被丢掉，要么按 WGS84 解释；原始 SRID 不是 4326 的话，先做投影转换。环的绕向、空几何、Z 值在不同工具里处理也不一致，转完最好抽几个点核对位置。需要互转时用 [矢量格式转换](/zh/tools/format-convert/)，XML 形式的几何见 [GML](/zh/guide/gml/)，带属性的 JSON 结构见 [GeoJSON](/zh/guide/geojson/)。

批量处理时，逐条调用数据库函数通常比在应用层拼字符串靠谱；手拼容易漏逗号、漏括号，还会把没校验过的输入直接塞进 SQL。

## 示例数据与解析脚本

仓库里有三个示例几何的文本文件，附对应的解析脚本：[sample.wkt](/examples/data/sample.wkt) 与 [wkt_parser.py](/examples/python/wkt_parser.py)。脚本用 shapely 做完整语法解析，输出 GeoJSON FeatureCollection；可选的 `SRID=` 前缀会被剥掉，但不做投影转换，属性保持为空。用法为 `python wkt_parser.py sample.wkt -o out.geojson`。
