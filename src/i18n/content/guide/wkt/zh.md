WKT（Well-Known Text）是 OGC 定义的几何文本表示法。它只描述几何，不带属性，非常适合数据库字段、日志和单条几何交换。

## 最小可用示例

```text
POINT (116.3974 39.9088)
LINESTRING (116.39 39.90, 116.40 39.91, 116.41 39.92)
POLYGON ((116.39 39.90, 116.41 39.90, 116.41 39.92, 116.39 39.90))
MULTIPOLYGON (((116.39 39.90, 116.41 39.90, 116.41 39.92, 116.39 39.90)))
GEOMETRYCOLLECTION (POINT (116.3974 39.9088), LINESTRING (116.39 39.90, 116.40 39.91))
```

- **坐标顺序是 x y**，地理场景通常就是经度、纬度。
- **多边形双层括号**：外层是环列表，内层是一个环；第一个是外环，其余是洞。
- **环必须闭合**，首尾坐标相同。
- **支持 Z / M**：`POINT Z (116.3974 39.9088 44)`。

除上面五种，还常用 `MULTIPOINT`、`MULTILINESTRING`，以及 `POINT EMPTY`、`GEOMETRYCOLLECTION EMPTY` 这类空几何。空几何表示位置未知但记录存在，数据库导出时可能被写成 `NULL` 或直接省略，读取时要把两者分开处理。

## 结构与字段说明

WKT 只有类型关键字和坐标，没有键值对，也没有属性表。解析器通常在读到括号时开始收集数字，因此空格、逗号和括号的数量必须严格匹配。

| 组成 | 是否必需 | 常见取值或单位 |
| --- | --- | --- |
| 类型关键字 | 必需 | POINT、LINESTRING、POLYGON、MULTIPOINT、MULTILINESTRING、MULTIPOLYGON、GEOMETRYCOLLECTION |
| 维度标记 | 可选 | Z 表示高程，M 表示度量，ZM 表示两者；省略即二维 |
| 坐标元组 | 点、线、面均需要 | 数字之间用空格分隔；地理坐标通常是十进制度 |
| 括号层级 | 必需 | 点一层，线一层，面两层，多重面三层 |
| 环闭合 | 多边形必需 | 首尾坐标完全相同，合法环至少四个点 |
| SRID 前缀 | 标准中不存在 | 仅 PostGIS EWKT 使用，写法为 `SRID=4326;` |

坐标本身不带单位。`116.3974` 既可能是度，也可能是米，只能由外部约定判断。地理坐标系一般按经纬度理解，投影坐标系则以米或英尺计，两者混用往往不会报错，只会得到错误位置。Z 值的单位同样靠约定，常见为米，文件中不会声明。

同一几何在不同规范版本中的写法并不完全一致。较新的文本规范允许把维度标记写在类型名之后，也允许在集合里继续嵌套集合；旧解析器可能只认二维写法。跨系统传递前，先用目标工具解析一小段样本，比读完整份规范更快。

## SRID 与 EWKT

标准 WKT 不包含坐标系。数据库里常见的：

```text
SRID=4326;POINT (116.3974 39.9088)
```

是 PostGIS 的 EWKT 扩展。看到 SRID 前缀时，要确认目标工具是否支持；不支持的解析器会直接把整串判为非法。

EWKT 只存在于 PostGIS 生态。PostGIS 用 `ST_GeomFromEWKT` 读取带前缀的字符串，用 `ST_AsEWKT` 输出；如果改用 `ST_GeomFromText`，就要把 SRID 作为第二个参数传入，字符串里不能再带前缀。数据库列通常自带 SRID 约束，导出成纯 WKT 后这层信息就丢了，跨系统传递时需要单独记录。

## 常见错误与陷阱

- **经纬度写反**：现象是点落到地球另一侧或海里；原因是把纬度放在了前面；后果是地图仍能加载，但所有位置都错，而且没有任何报错。
- **环没有闭合**：现象是导入时报 ring not closed，或面积算出来为零；原因是首尾坐标只写了一次；后果是该记录被拒收，批量导入时可能整批中断。
- **括号层级不对**：现象是解析器报语法错误；原因是 POLYGON 写成单层括号，或 MULTIPOLYGON 少一层；后果是整个文件无法读取，错误往往在很靠后的位置才暴露。
- **把 EWKT 当成通用 WKT**：现象是转换工具报非法几何；原因是字符串前面带了 `SRID=4326;`；后果是整串被拒绝，或者前缀被静默剥掉后坐标按错误的坐标系解释。
- **随意截断小数位**：现象是相邻点重合、线条出现锯齿；原因是只保留两三位小数；后果是测量精度永久损失，无法从输出反推原始坐标。
- **多边形自相交**：现象是面积异常或空间查询漏结果；原因是环的边彼此交叉；后果是部分数据库允许写入但把几何标记为无效，后续叠加分析不可信。

## 限制

- **只能表达一条几何**：多个要素需要多行或多条记录。
- **没有属性**：业务字段必须另存。
- **没有样式与时间**。
- **坐标精度完全依赖写出的字符串**，不要用固定小数位截断测量数据。

WKT 也不表达拓扑关系。相邻的多边形各自保存公共边，边界一旦修改就要同步两处；需要共享边的数据应改用拓扑格式。文本形式还意味着同样的坐标会以字符而非二进制重复存储，在百万级要素场景下体积和解析时间都不占优势。

文本可读性也带来版本管理上的便利：几何变化能直接出现在 diff 里。代价是不能像二进制那样按字节校验，手工改动一个数字就会改变几何，而且不会留下修改痕迹。

## 与相邻格式对比

| 维度 | WKT | GeoJSON | WKB |
| --- | --- | --- | --- |
| 数据范围 | 单条几何，可嵌套集合 | 要素集合，含属性 | 单条几何，二进制 |
| 坐标系 | 本身不声明，EWKT 例外 | 固定 WGS84 | 由外部约定 |
| 可读性 | 高，纯文本 | 高，JSON | 低，需要解码 |
| 体积 | 小 | 较大，键名重复 | 最小 |
| 属性能力 | 无 | 有 properties | 无 |
| 典型用途 | 数据库字段、日志、测试用例 | Web 传输、前端渲染 | 数据库内部存储、批量传输 |

WKT 与 WKB 描述的是同一套几何模型，只是编码不同。WKB 用字节表示类型和坐标，体积更小、解析更快，但不可读，适合程序之间传递。GeoJSON 多了属性和集合结构，适合浏览器和 HTTP 接口，代价是键名重复带来的体积膨胀。需要同时保留属性和文本可读性时，GeoJSON 更合适；只需要一条几何、希望直接贴进 SQL 或日志时，WKT 更直接。

## 转换与工具入口

WKT 转 GeoJSON 时，SRID 会被丢弃或按 WGS84 解释；如果原始 SRID 不是 4326，要先做投影转换。环的绕向、空几何和 Z 值在各工具中的处理也不一致，转换后应抽查几个点核对位置。需要互转时用 [矢量格式转换](/zh/tools/format-convert/)，XML 形式的几何见 [GML](/zh/guide/gml/)，带属性的 JSON 结构见 [GeoJSON](/zh/guide/geojson/)。

批量处理时，逐条调用数据库函数通常比在应用层拼接字符串可靠；拼接容易漏掉逗号或括号，也会把未经校验的输入直接带进 SQL。

## 示例数据与解析脚本

仓库里提供了三个示例几何的文本文件和对应的解析脚本：[sample.wkt](/examples/data/sample.wkt) 与 [wkt_parser.py](/examples/python/wkt_parser.py)。脚本基于 shapely 解析完整语法，输出 GeoJSON FeatureCollection；它会剥掉可选的 `SRID=` 前缀，但不做投影转换，属性保持为空。用法为 `python wkt_parser.py sample.wkt -o out.geojson`。
