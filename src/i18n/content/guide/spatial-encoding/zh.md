坐标是两个浮点数，放进 URL、日志行和缓存键里都嫌长。把位置压缩成短字符串，可以缩短参数，让日志可读、缓存键稳定，也能在分享时主动降低精度。GeoHash 与 Plus Codes 是两类最常见的做法：前者从空间索引出发，后者从「给人读的地址」出发。

两者都能离线计算，不需要数据库，也不依赖网络。导航、配送、日志分析和应急调度都会用到它们：有的把编码当索引键，有的把它印在门牌或救援卡上。选择哪一种，取决于更在意前缀检索、口述分享，还是隐私分级。

## 最小示例

以天安门 39.9088, 116.3974 为例。GeoHash 取 7 位得到 `wx4g09n`，取 5 位得到 `wx4g0`；位数越少，格子越大。Plus Codes 得到 `8PFRW95W+GX`，10 个字符加一个加号，格子约为十几米。

```text
纬度 39.9088, 经度 116.3974
GeoHash 7 位: wx4g09n
GeoHash 5 位: wx4g0
Plus Code:    8PFRW95W+GX
```

GeoHash 没有分隔符，长度由调用方决定，常见 5 到 9 位。Plus Codes 的完整码固定为 8 个字符、一个加号、再 2 个字符，也可以多一位变成 11 位，例如 `8FVC9G8F+6W` 就是 8 字符加号 2 字符的结构。

## 结构与字段表

### GeoHash

GeoHash 用 32 个字符表示位置：`0123456789bcdefghjkmnpqrstuvwxyz`。字母统一小写，去掉了 `a`、`i`、`l`、`o` 四个容易与数字混淆的字符。

编码过程是对经度和纬度分别做二分：先按经度判断落在哪一半，再按纬度判断，交替进行，每 5 个比特查一次字符表，得到一个字符。字符越多，格子越小。因为每一级都在上一级格子里继续切分，所以短前缀一定是长编码的前缀，这就是它能直接做字符串范围查询的原因。

| 位数 | 格子尺寸（约） | 典型用途 |
|---|---|---|
| 1 | 5000 km | 大洲级分区 |
| 3 | 156 km | 省或大区聚合 |
| 4 | 39 km × 20 km | 城市级缓存 |
| 5 | 4.9 km | 城区、配送片区 |
| 6 | 1.2 km × 0.6 km | 街区、附近搜索 |
| 7 | 153 m | 建筑、路口 |
| 8 | 38 m × 19 m | 门店、站点 |
| 9 | 4.8 m | 门牌级定位 |

位数每加 1，格子面积缩小到约 1/32，边长缩小到约 1/5.7。查询附近对象时，常见做法是先取目标点的 7 位编码，再算出东、西、南、北、东北、西北、东南、西南八个邻居，把九宫格一起作为前缀条件。只查中心格子会漏掉边界另一侧的点。

GeoHash 的格子是经纬度网格，与行政区、道路无关。两个相距几十米的点，如果正好跨过格子边线，7 位编码可能完全不同，只有更短的前缀相同。这也是九宫格邻居不可省略的原因。

隐私保护常靠截断后缀实现：保留 5 位约 4.9 公里，保留 6 位约 1.2 公里。截断后的编码仍然对应一个矩形，不是圆，也不保证匿名。人口密集区里，粗粒度的位置配合时间、设备等信息仍可能被还原，敏感场景需要更严格的措施。

### Plus Codes

Plus Codes 又称 Open Location Code，使用 20 个字符：`23456789CFGHJMPQRVWX`。字母统一大写，去掉了元音以及 `0`、`1`、`I`、`L`、`O`、`U` 等容易看错的字符，减少误读和拼出意外单词的可能。

字符按「对」组织：一对字符分别编码纬度和经度。前 5 对构成 10 位完整码，分辨率依次是 20°、1°、0.05°、0.0025°、0.000125°。前 4 个字符定义 1° × 1° 的区域码，尺度约一百公里；10 位码的格子约 14 米；再补第 11 位时，把格子按 4 列 5 行继续切分，精度到 3 米左右。

完整码在全球唯一，不需要参考点。短码则省略开头的 4 个字符，必须配合一个附近地点才能还原。例如天安门的完整码是 `8PFRW95W+GX`，在北京范围内可以写成 `W95W+GX`；换到另一座城市用同一个短码，可能还原到错误的一度网格。

短码不是「去掉后缀」，而是「去掉前缀」。它不满足 GeoHash 那种前缀包含关系，不能直接拿来做字符串范围查询。Plus Codes 的设计目标是口述和书写：字符少、有加号分隔、可以印在门牌上，在没有正式街道地址的地区尤其有用。整个编码只依赖坐标本身，离线也能算，不需要地址库或地理编码服务。

### S2 与 H3

S2 与 H3 是另外两类常见的空间索引。S2 把球面映射到立方体再逐级细分，单元编号是 64 位整数，沿 Hilbert 曲线排列；H3 用二十面体上的六边形网格，编号同样是整数，层级由分辨率参数决定。

它们的共同点是：单元 ID 不面向人阅读，需要库来计算、取边界和找邻居；优势是层级清晰、索引紧凑，适合数据库分片、聚合统计和大规模空间检索。需要口述或印在纸面时，GeoHash 与 Plus Codes 更合适。

## 常见错误与陷阱

**把 GeoHash 前缀当成精确范围。** 现象是查询漏掉了紧邻边界的对象，或者以为 7 位编码对应一个半径 150 米的圆。原因是前缀描述的是矩形格子，格子外的邻近点编码不同，而且格子随纬度变窄。后果是附近搜索出现漏检，距离越远越明显。处理方式是取九宫格邻居，再按真实距离过滤。

**截断 GeoHash 就当作匿名化。** 现象是公开发布 6 位编码后，仍能定位到具体小区。原因是 6 位约 1.2 公里，配合时间、设备标识和业务数据足以缩小范围。后果是隐私泄露，而且很难在事后收回。处理方式是按场景评估精度，必要时加入随机偏移，或不发布精确时间。

**短 Plus Code 脱离参考点使用。** 现象是 `W95W+GX` 在另一座城市可能解码到完全错误的位置。原因是短码省略了开头的区域码，还原时必须提供一个足够近的参考坐标。后果是位置偏差可能达到上百公里，而且解码过程不会报错。处理方式是分享时附带城市名，或直接使用 10 位完整码。

**把 Plus Code 当成邮政地址。** 现象是快递面单或表单系统无法识别，仍要求填写街道门牌。原因是 Plus Code 是坐标编码，不含行政区和门牌语义，也不保证与投递系统对接。后果是地址无法直接使用，需要人工转换。处理方式是与传统地址并列使用，作为补充定位。

**混用两套字符表。** 现象是把 GeoHash 里的小写 `o` 看成数字 `0`，或在 Plus Code 里写入 `O`、`I`、`L`。原因是两套字母表都刻意删除了易混字符，但删除的集合不同。后果是解码失败，或者落到相邻的错误格子。处理方式是编码后按各自字符表校验，解码前统一大小写。

**在极区或反经线附近直接算邻居。** 现象是经度从 179.9 跳到 -179.9，邻居编码出现在地球另一侧。原因是经度需要环绕处理，纬度需要在极点截断。后果是附近查询漏点或取到无效格子。处理方式是先把经度归一化到 ±180，再单独处理极区。

## 与相邻编码对比表

| 维度 | GeoHash | Plus Codes | S2 / H3 |
|---|---|---|---|
| 可读性 | 小写字母数字，无分隔 | 大写字母数字，含加号，像短地址 | 64 位整数或十六进制，不可读 |
| 精度分级 | 每加 1 位，边长约缩至 1/5.7 | 每对字符把经纬度各细分 20 份，末位再切 4 × 5 | 层级由库定义，整数编码 |
| 是否需要参考点 | 否 | 完整码不需要，短码需要 | 否 |
| 索引友好度 | 高，字符串前缀可直接范围扫描 | 中，完整码有层级，短码不适合索引 | 高，整数 ID 与层级适合数据库 |
| 隐私 | 截断后缀即可降低精度 | 去掉前缀得到短码，或直接舍入坐标 | 可按层级聚合，粒度明确 |
| 典型用途 | 缓存键、附近搜索、日志聚合 | 口述地址、无门牌地区、紧急定位 | 大规模空间索引、六边形分析 |
| 文本形式 | 5 到 9 个字符 | 10 或 11 位，含一个加号 | 非文本 |

如果需求是「把位置放进 URL 或缓存键，并且要按区域做前缀查询」，GeoHash 更直接。如果需求是「让人念出来、写在纸上、在没有门牌的地方定位」，Plus Codes 更合适。如果需求是「在数据库里对海量点做层级聚合」，S2 或 H3 的整数编码更省空间。

## 转换与工具入口

本站提供两个编码工具：[GeoHash 编解码](/zh/tools/geohash/) 支持坐标与字符串双向转换，可以选择位数，也能批量处理；[Plus Codes](/zh/tools/plus-codes/) 支持经纬度与完整码互转，短码需要参考地点，工具不接受短码输入。

两个工具都在浏览器本地计算，不上传坐标，适合处理不便外发的数据。转换时注意精度差异：GeoHash 解码得到的是格子中心点，再编码成 Plus Code 时，结果对应的是这个中心点，不是原始坐标。往返一次不会还原原始数值，只会落在同一个格子内。

日志里已经存了 GeoHash 时，可以先解码成中心点，再转成 Plus Code 用于分享；反过来也成立。需要批量校验时，先在 GeoHash 工具里统一位数，再逐条转换，避免同一批数据混用 5 位和 7 位。

## 示例数据与解析脚本

下面几个坐标与两套编码的结果可以用来校验自己的实现：

| 地点 | 纬度 | 经度 | GeoHash 7 位 | Plus Code |
|---|---|---|---|---|
| 天安门 | 39.9088 | 116.3974 | `wx4g09n` | `8PFRW95W+GX` |
| 时代广场 | 40.7580 | -73.9855 | `dr5ru7v` | `87G8Q257+6Q` |
| 悉尼歌剧院 | -33.8568 | 151.2153 | `r3gx2ux` | `4RRH46V8+74` |
| 赤道与本初子午线 | 0 | 0 | `s000000` | `6FG22222+22` |

GeoHash 的编码只用标准库就能写出来：

```python
ALPHABET = "0123456789bcdefghjkmnpqrstuvwxyz"

def geohash(lat, lng, length=7):
    lat_range, lng_range = [-90.0, 90.0], [-180.0, 180.0]
    bits, even = [], True
    while len(bits) < length * 5:
        rng = lng_range if even else lat_range
        value = lng if even else lat
        mid = (rng[0] + rng[1]) / 2
        upper = value >= mid
        bits.append(int(upper))
        rng[0 if upper else 1] = mid
        even = not even
    return "".join(
        ALPHABET[sum(bit << (4 - i) for i, bit in enumerate(bits[j:j + 5]))]
        for j in range(0, len(bits), 5)
    )

print(geohash(39.9088, 116.3974, 7))
```

运行结果应为 `wx4g09n`。这段代码只做编码；解码时按同样的顺序把字符还原成 5 个比特，再不断收窄经纬度区间，最后取区间中点。

Plus Codes 的前 4 位可以用同样的交替二分写出：把纬度加 90、经度加 180，依次按 20° 和 1° 取整除，再查 20 字符表。后面 3 对继续按 0.05°、0.0025°、0.000125° 细化，第 11 位再按 4 列 5 行切分。参考实现和完整规范见 [google/open-location-code](https://github.com/google/open-location-code)，提供多种语言版本。

解析前先做字符表校验。GeoHash 中出现 `a`、`i`、`l`、`o` 一定是错的；Plus Codes 中出现 `0`、`1`、`I`、`L`、`O`、`U`，说明字符表用错了。短码还原时，参考点越近越可靠，超出同一个区域码时应当直接拒绝，而不是返回一个看似合理的结果。
