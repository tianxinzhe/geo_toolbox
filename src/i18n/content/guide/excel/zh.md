Excel 是最常见的坐标数据来源，也是最不适合作为程序交换格式的选择。它方便人编辑，却会在保存和显示过程中悄悄改变数值。

问题不在于 Excel 做错了什么，而在于它把「显示」和「存储」分成两层：单元格里可能是一个数字，显示出来却是日期；可能是一个公式，缓存里却是旧结果；可能是一整块合并区域，真实值只存在于左上角。程序读到的是存储层，人看到的是显示层，两者不一致时，表格看起来完全正常。

## XLSX 的内部结构

XLSX 不是纯文本，而是一个 ZIP 容器：

```text
example.xlsx
├─ [Content_Types].xml
├─ xl/workbook.xml
├─ xl/worksheets/sheet1.xml
├─ xl/sharedStrings.xml
└─ xl/styles.xml
```

工作表数据在 `sheet1.xml`，文本常放进共享字符串表。旧版 `.xls` 使用二进制 BIFF 结构，与 XLSX 完全不兼容，现代工具通常需要额外库才能读取。

这套结构由 Office Open XML 规范定义（ECMA-376）。`workbook.xml` 记录有哪些工作表、顺序和隐藏状态；每张表对应一个 `worksheets/sheetN.xml`；`sharedStrings.xml` 把所有文本集中存一份，单元格只保存索引；`styles.xml` 保存数字格式，日期之所以显示成日期，靠的是这里的格式编号，而不是单元格里真的存了日期。单元格本身还有一个 `t` 属性表示类型：不带 `t` 是数字，`s` 是共享字符串，`inlineStr` 是内联字符串，`str` 是公式返回的字符串，`b` 是布尔值，`e` 是错误值。

## 最小可用示例：坐标数据怎么放

推荐两种布局：

| 布局 | 列 | 适用 |
|---|---|---|
| 经纬度列 | `name, lng, lat` | 纯点数据 |
| WKT 列 | `name, geom` | 含线、面或复杂几何 |

经纬度列要保持数值格式，不要加单位或方向字母；WKT 列要确保单元格是文本，避免 Excel 自动换行或截断。

Excel 同样没有坐标系字段。工作簿里写 `lng, lat`，只能说明这两列是经纬度，不能说明是 WGS84、CGCS2000 还是某个投影。交付时要把 EPSG 代码写在说明文档或单独的工作表里，不要指望从数值本身推断。另一种常见做法是把 WKT 列设成「文本」格式再粘贴，否则以 `+`、`-`、`=` 开头的内容可能被当作公式。

## 结构与字段说明

| 部件或字段 | 作用 | 是否必需 | 常见取值 |
|---|---|---|---|
| `[Content_Types].xml` | 声明各部件类型 | 必需 | XML |
| `xl/workbook.xml` | 工作表列表与顺序 | 必需 | `sheet1`、`Sheet1` |
| `xl/worksheets/sheetN.xml` | 单元格数据 | 至少一个 | A1 引用、行列号 |
| `xl/sharedStrings.xml` | 共享文本表 | 可选 | 字符串数组 |
| `xl/styles.xml` | 数字格式、字体、边框 | 可选 | 日期格式、小数位 |
| 单元格 `t` | 值类型 | 可选（默认数字） | `s`、`inlineStr`、`str`、`b`、`e` |
| `date1904` | 日期系统开关 | 可选 | `0` 或 `1` |

读 XLSX 时容易忽略两点。第一，单元格是稀疏存储的：空单元格不会出现在 XML 里，按行列遍历时必须自己补空，否则后面的列会整体左移。第二，日期系统的起点有两套。默认的 1900 系统以 1900 年 1 月为起点；Mac 旧版文件可能设置 `date1904="1"`，同样一个日期序列号会相差 1462 天。读取方若不检查这个开关，整列日期都会偏四年。

## 六个会改坏数据的行为

### 日期变序列号

**现象**：`2026-11-09` 读出来是 `46335`，或者整列变成 `1900-01-00` 附近的值。

**原因**：单元格里存的从来不是日期文本，而是一个数字，日期只是套在上面的显示格式。程序若只读值、不看格式，拿到的是序列号。

**后果**：时间字段全部变成五位数，按时间筛选、排序、计算间隔都会错。

### 长数字变科学计数法，末位变零

**现象**：地块编号 `1101050010030000123` 显示成 `1.10105E+18`，后几位变成 0。

**原因**：Excel 把数值存成双精度浮点数，只保证约 15 位有效数字。超过这个长度的编号在打开或粘贴时就被转成数字，多余位数直接丢失。

**后果**：编号不再唯一，两份数据无法按编号关联。这个损失发生在导入那一刻，之后再改格式也补不回来。

### 前导零消失

**现象**：行政区代码 `00123` 变成 `123`。

**原因**：列被当作数字处理，前导零没有数值意义。

**后果**：代码与标准代码表对不上，匹配全部失败。需要保留前导零时，列要在导入前设为文本，或使用导入向导指定为文本列。

### 公式未计算

**现象**：本应是距离或面积的那一列，读出来是 `=B2*111320` 这样的字符串，或者空值。

**原因**：XLSX 保存公式文本和缓存结果两份内容。程序默认可能读公式，也可能因为文件由第三方库生成而没有缓存值。

**后果**：属性缺失或类型错误。交付前应把公式列复制、选择性粘贴为值，再保存。

### 合并单元格让表头错位

**现象**：表头只有第一列有内容，其余列读出来是空；或者数据行整体偏移。

**原因**：合并区域只在左上角单元格保存值，其余单元格在文件里是空的。双层表头、跨列标题都会造成这种结构。

**后果**：列名匹配失败，后面的列被当成无名列；按行读取时行宽不一致，坐标落到错误的列。

### 多工作表与隐藏列

**现象**：读到的不是想看的那张表，或者少了几列。

**原因**：一个工作簿可以有多张表，解析器通常只取第一张；隐藏行列仍然占位，但有些导出流程会跳过。

**后果**：数据整体错位或缺失，而且文件打开时看不出异常，因为人看到的是当前选中的那张表。

## 正确的交付方式

- 在 Excel 里完成编辑后，**另存为 CSV UTF-8**，再交给转换工具。注意「另存为 CSV」只导出当前工作表，其他工作表不会一起保存。
- 如果必须交付 XLSX，明确告知工作表名称、表头行和坐标列。
- 不要用 Excel 直接打开再保存已经生成的 CSV，否则编码和数字格式可能被再次改写。

另外两条经验：交付前把公式列转成值，把日期列确认成文本或明确的 ISO 日期；如果表格里混着标题行、说明行和空行，先在 Excel 里清理干净，不要让解析器去猜哪一行才是表头。

## 与相邻格式对比

| 格式 | 结构 | 几何能力 | 坐标系 | 适合 |
|---|---|---|---|---|
| XLSX | ZIP + XML | 点；线面靠 WKT 列 | 无声明 | 人工整理、核对、评审 |
| CSV / TSV | 纯文本 | 点；线面靠 WKT 列 | 无声明 | 程序交换、批量导入 |
| GeoJSON | JSON 文本 | 点线面全集 | 默认 WGS84 | 网页地图、接口 |
| GeoPackage | SQLite 数据库 | 点线面、多图层 | 有 SRS 表 | GIS 工程、离线数据 |

Excel 的优势在编辑体验：颜色、批注、冻结窗格、多表对照，都是纯文本给不了的。劣势在可交换性：二进制容器、隐藏格式、公式与显示层的差异，任何一项都可能让程序读到与人看到不同的内容。需要长期保存或程序读取时，CSV 更稳；需要几何与坐标系时，GeoJSON 或 GeoPackage 更合适。

## 转换与工具入口

需要把 Excel 或 CSV 转成矢量数据，用[矢量格式转换](/zh/tools/format-convert/)；它只读第一张工作表，公式取缓存值。坐标如果是投影单位，先用[投影坐标转换](/zh/tools/epsg-convert/)换到 EPSG:4326。表格格式的细节见 [CSV 与 TSV](/zh/guide/csv-tsv/)，整体选型见 [15 种矢量格式总览](/zh/guide/vector-formats/)。

## 示例数据与解析脚本

- [sample.xlsx](/examples/data/sample.xlsx)、[xlsx_parser.py](/examples/python/xlsx_parser.py)

样例是一张工作表，列为 `lng,lat,name,kind`，内容与 CSV、TSV 样例一致。脚本依赖 openpyxl：

```bash
pip install openpyxl
python xlsx_parser.py sample.xlsx -o out.geojson
```

脚本只读第一张工作表，公式取缓存值，其余列转成属性。样式、批注和其他工作表会被忽略。
